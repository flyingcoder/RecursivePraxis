# Suggestion — commands are for humans, skills are for host agents

Status: suggestion. See [NOTICE.md](NOTICE.md). This document answers the
redundancy that [generated-file-inventory.md](generated-file-inventory.md)
measured but did not resolve: `lambda init` writes a skill and a command per
workflow that differ by **one line**, so half the generated bytes are a copy.

The claim here is that this is not a rendering defect and not a bug in the
render pipeline. It is a **content-model defect**: there is one class of
authored body, and it is being emitted to two surfaces that should be saying
different things to different readers.

The proposal: **a skill is reference material for a host agent; a command is a
task entry point for a human; a command composes one or more skills.**

OpenSpec was reviewed as a reference. The finding is not the one you would
expect, and it is in §2.

---

## Frame — what the generated files are for

Added 2026-08-26 from maintainer clarification. This section reframes the rest
of the document; where it and a later section disagree, this one is correct.

RecursivePraxis is **a zero-shot agentic methodology that progressively
constructs its own contextual examples and constraints through a calculated
sequence of lambda operators.** The operators do not replace a model's
reasoning or its cognitive architecture — today's models already have both.
They *guide* an existing reasoner through a sequence.

### The layer this occupies

An AI-assisted development conversation already runs three stages. This inserts
a fourth:

| | Stage | Whose |
| --- | --- | --- |
| 1 | **intent** — the human states what they want | human |
| 2 | **intent processing** — the model parses it with its own reasoning | model |
| 3 | **intent operation** — ask the kernel for a legal operator sequence, and follow it | **RecursivePraxis** |
| 4 | **intent execution** — the model does the work | model |

Stage 3 is the whole product surface. It is not a planner and not a replacement
for stage 2: by the time it runs, the model has already understood the request.
What it adds is a *calculated sequence* that stage 4 follows, and the context
and constraints that sequence accumulates along the way.

### The acceptance test

Generated files are correct if, and only if, a host agent that has loaded them
can do three things:

1. **Know how to ask for a lambda sequence** — recognise that a task has
   reached stage 3 and that a sequence is what to request.
2. **Call the lambda verbs to get the sequence** — reach the right verb with
   the right arguments and receive a sequence back.
3. **Execute the sequence** — verify it, apply it operator by operator, and
   read the result.

All three are **host-agent** capabilities. None of them is a human capability.
This is the measure to hold the rest of this document against, and §7 scores
today's output against it.

### What this corrects in the sections below

- The audience table in §3 said commands are "for the human." That is wrong as
  written. A command is **triggered by** a human and **addressed to** the
  agent. Both surfaces are written to the agent; they differ in what starts
  them and what they answer. §3 is corrected in place.
- §4's `/praxis-commit` was described as "finalize the session" with a naming
  concern about `git commit`. Both were wrong; §4 is corrected in place.
- The lambda verbs are not merely "reference material." They are **reusable
  primitives designed to be called in sequence**. §1's diagnosis of the
  redundancy still holds; its characterisation of the seven as a passive
  catalogue understates them.

## 0. The redundancy, measured

From a captured run of `lambda init --tools cursor --scope project`:

| | |
| --- | --- |
| Files written for Cursor | 14 |
| Total bytes | 40,279 |
| Bytes in the 7 command files | 20,035 (49.7%) |
| Lines by which a command differs from its skill | **1** |

The one line is frontmatter `name:` — `diff` any generated skill against its
command and that is the only hunk. Body, epistemic footer, managed markers, and
`description` are identical across all seven pairs.

Two further facts about the command surface as it exists today:

- **No command takes an argument.** There is no `$ARGUMENTS`, no `{{args}}`,
  no positional token anywhere in `src/` (verified by grep). A command that
  cannot receive input from the human who typed it is not doing command work.
- **Every workflow body is written to the agent, not the human.** Read
  `praxis-status.md` as a person: it tells you to run `lambda status --json`
  and how to interpret `legalNext`. A human at a terminal would type
  `lambda status`. The `/`-prefix adds nothing.

## 1. Root cause

All seven workflows ([workflows.ts](../../src/init/workflows.ts)) answer the
same question: *how do I call and interpret one `lambda` verb?*

| Workflow | Verb it wraps |
| --- | --- |
| `status` | `lambda status` |
| `analyze` | `lambda analyze` |
| `solve` | `lambda solve` |
| `diagnose` | `lambda diagnose` |
| `session` | `lambda sense` / `step` / `halira` / `bind` |
| `ir` | `lambda ir` |
| `intent` | `lambda diagnose` + `operators show` (the one partial exception) |

That is a **skill catalogue**. It is reference material an agent loads when it
needs to touch the kernel — one entry per verb, which is the right shape for
that job.

There is currently **no command content at all**. So the generator, having
nothing else to put in a command file, puts the skill body there. The
duplication is downstream of a missing content class, and no amount of
render-pipeline work fixes it — a second copy of the right content is still
the wrong content for that surface.

`intent` is the tell. It is the only workflow that opens with a human's
unstructured request and walks a five-step procedure to an output — and it is
the only one that reads like a command. It is currently filed as a skill
because that is the only class that exists.

## 2. What OpenSpec actually does

Reviewed from source at `Fission-AI/OpenSpec@main` (fetched this session), not
from its documentation alone.

### 2.1 The headline finding: OpenSpec has the same problem, worse

OpenSpec authors a skill template and a command template **as two separate
hand-maintained string literals per workflow**. Measured overlap:

| Template module | Skill | Command | Identical lines |
| --- | ---: | ---: | ---: |
| `workflows/propose.ts` | 137 | 137 | 134 — **97%** |
| `workflows/new-change.ts` | 65 | 64 | 59 — **90%** |

The 10% that differs in `new-change.ts` is entirely invocation phrasing:

| Skill says | Command says |
| --- | --- |
| "The user's request should include a change name" | "The argument after `/opsx:new` is the change name" |
| "…or ask me to continue." | "Run `/opsx:continue` or just describe…" |
| "suggest continuing that change instead" | "suggest using `/opsx:continue` instead" |

That is the same content, hand-copied, free to drift — and it *is* drifting, at
one line per ten. RecursivePraxis renders both surfaces from one body through
one pipeline, so its two files **cannot** disagree. On this axis
RecursivePraxis is ahead, and copying OpenSpec's content model would be a
regression.

### 2.2 OpenSpec is migrating toward the RecursivePraxis model

`workflows/apply-change.ts` has already been refactored: a single
`getApplyInstructions()` is consumed by both `getApplyChangeSkillTemplate()`
and `getOpsxApplyCommandTemplate()`. Its header comment states the principle
RecursivePraxis enforces structurally:

> The apply workflow instructions, authored once and rendered by both the skill
> and command surfaces. The surfaces are intentionally distinct, but they
> differ only in how they are invoked — the generation transformers rewrite the
> canonical `/opsx:<id>` tokens per surface downstream […]. The instruction
> text itself is shared, so the two cannot silently drift.

So: `apply` is DRY, `propose` and `new` are not. OpenSpec is mid-migration to
where this project already stands. **Take its mechanisms, not its content
model.**

### 2.3 Three mechanisms worth taking

**(a) Delivery mode as a per-tool knob.** OpenSpec carries
`delivery: 'both' | 'skills' | 'commands'`
(`getTransformerForTool` in `src/utils/command-references.ts`). A tool can be
configured to receive skills only, commands only, or both. RecursivePraxis
derives this implicitly from the layout class and offers no choice.

**(b) An explicit command → skill map.** `COMMAND_TO_SKILL_NAME` maps each
command id to the skill that backs it:

```ts
const COMMAND_TO_SKILL_NAME: Record<string, string> = {
  'explore': 'openspec-explore',
  'apply':   'openspec-apply-change',
  'propose': 'openspec-propose',
  …
};
```

This is the seam the proposal here needs. Note that OpenSpec's map is strictly
**1:1** — a command backs exactly one skill. The many-to-one composition asked
for here (`/praxis-debug` loading three skills) is an extension beyond what
OpenSpec does, not a copy of it.

**(c) Reference degradation, which is the part RecursivePraxis is missing.**
OpenSpec rewrites a canonical `/opsx:<id>` reference differently depending on
what the target tool actually received:

| Situation | `/opsx:apply` becomes |
| --- | --- |
| Tool gets commands, namespaced layout | `/opsx:apply` |
| Tool gets commands, flat layout | `/opsx-apply` |
| Tool gets commands, prompt library (Amazon Q) | `@opsx-apply` |
| Tool gets **skills only** | `/openspec-apply-change` — the *skill* |
| Codex (skills invocable by `$`) | `$openspec-apply-change (Codex) or /openspec-apply-change (other agents)` |
| Tool has **no slash surface** (Rovo Dev) | `the openspec-apply-change skill` — prose |

The stated reason: *"so those skills never point at commands that were not
generated."*

RecursivePraxis's `remarkPraxisInvocation`
([source](../../src/render/plugins/remark-praxis-invocation.ts)) does the same
per-host rewrite and does it better — on the mdast tree rather than by regex on
a string, so Codex's `$` and bracket-adjacent forms cannot come out
backslash-escaped. But it has **only the command spelling**. It cannot degrade
a reference to a skill, because today every host gets a 1:1 pair and the case
never arises. **Under the split it arises immediately** — see §5.3.

## 3. The proposed content model

Two authored classes instead of one.

| | **Skill** | **Command** |
| --- | --- | --- |
| Triggered by | the agent matching on `description` | a human typing `/praxis-<id>` |
| Addressed to | the host agent | the host agent — **both**, see Frame |
| Answers | "how do I call and read `lambda <verb>`" | "what sequence do I ask for, and how do I run it, for task *Y*" |
| Stage it serves | 3, once already entered | **the entry into stage 3** |
| Takes arguments | no | **yes** — that is most of the point |
| Body shape | command · when to use · reading the output · epistemic constraints | intake · which skills to load, in what order · what to hand back |
| Cardinality | one per CLI verb | one per human task |
| Count today | 7 (the current workflows, unchanged) | 0 |
| Count proposed | 7 | 4 |

**A command's body is not instructions for doing the work.** It is a routing
document: what to ask the human, which skills to load in what order, what
constitutes done, and what to hand back. The *how* stays in the skills, authored
once. A command that restates a skill's procedure has reintroduced the
duplication in a new place.

### 3.1 Two new tokens

`{{invoke:<id>}}` exists and resolves to the host's command spelling. The split
needs two more:

| Token | Resolves to | Why it cannot be hardcoded |
| --- | --- | --- |
| `{{skill:<id>}}` | the skill's name **as this host loaded it** | `StandaloneLayout` names it `recursive-praxis-status`; `PluginLayout` names it bare `status`, because Claude Code requires the frontmatter `name` to match the plugin directory it was loaded from ([layouts.ts](../../src/hosts/layouts.ts)). A command that hardcodes either name is wrong on one of the two. |
| `{{args}}` | the host's argument token | Claude Code uses `$ARGUMENTS`; other hosts differ or append the text implicitly. Nothing in `src/` handles arguments today. Resolve it once per host, in the adapter, exactly as invocation is resolved. |

The precise spelling of `{{args}}` per host must be verified against each
vendor's current docs before implementation, and recorded in each adapter's
`verifiedAgainst` — the same discipline the path table already follows. It is
listed here as a required transform, not as a settled table.

## 4. The four commands

Each is grounded in verbs that exist. The D/C pairs are the authored constants
in [diagnose.ts](../../src/cli-commands/diagnose.ts), quoted, not invented.

### `/praxis-explore <topic>`
The human has a request they cannot yet state as a task.

Skills: `{{skill:intent}}` → `{{skill:diagnose}}` → `{{skill:analyze}}`.
Typical template `overwhelmed` (D 0.8/C 0.8 → 0.2/0.15, *"Excessive Ana without
Kata (no compression)"*). Must preserve `intent`'s `none` answer — a request
that matches no template is abstained on, not forced into the nearest fit.

### `/praxis-debug <symptom>`
Something is stuck or looping.

Skills: `{{skill:status}}` → `{{skill:diagnose}}` → `{{skill:session}}`.
Templates `stuck` (D 0.85/C 0.75 → 0.3/0.35, *"Meta ∘ Meta loop (infinite
reflection)"*) or `collapsed` (D 0.95/C 0.9 → 0.4/0.45, *"In the Void (∅), need
rescue operators"*). Verify with `lambda check` before acting on the sequence.

### `/praxis-polish <target>`
Work that is over-corrected and needs loosening — the inverse of debug.

Skills: `{{skill:diagnose}}` → `{{skill:analyze}}`. Template `rigid`
(D 0.15/C 0.1 → 0.5/0.5, *"Excessive Ortho (over-correction)"*). This is the
one template whose target D and C are *higher* than its initial, which is why
it earns a command of its own rather than a flag on `/praxis-debug`.

### `/praxis-commit`
**Commit-*message* guidelines. It does not run `git commit`.**

Given a set of code changes, it establishes the *motive* behind them, groups
the affected files by that motive, and writes the message under a fixed set of
constraints. The motive is the part a model will otherwise confabulate — it
reads a diff and narrates a plausible reason. Stage 3 exists to stop that: the
motive comes from a calculated sequence, not from the narration.

Shape: read the changes → obtain an operator sequence for them → one group per
operator → render each group under the repo's commit constraints.

Skills: `{{skill:status}}` → `{{skill:intent}}` → `{{skill:analyze}}`.

Two blockers, both verified in this checkout, both requiring a code change
outside this proposal:

- **The applied sequence is not readable.** `lambda status --json` returns
  `sequenceLength` — a number — and not `sequence`
  ([status-payload.ts](../../src/cli-support/status-payload.ts)). The session
  file holds the operators; the CLI does not surface them. A command that
  groups files by the operators actually applied cannot obtain them today
  without reading `.recursive-praxis/session.json` directly, which is not a
  documented interface.
- **`operators show` returns no meaning.** It prints exactly four lines —
  `name`, `symbol`, `class`, authored λ ([cli.ts](../../src/cli.ts), and
  verified by running it). See §7.2: this breaks a step the shipped `intent`
  skill already depends on.

Until the first is addressed, `/praxis-commit` must derive the motive from a
sequence it requests for the change rather than one it reads back — which is
the same path `{{skill:intent}}` already describes, and is why `intent` and not
`session` is the middle skill above.

Note what is *not* proposed: no command for `solve` or `ir`. Both are things an
agent needs mid-task, not things a human sets out to do. They stay skills, and
that asymmetry is the model working — the two surfaces are no longer required
to have the same cardinality.

### 4.1 What the difference looks like

The test is what a command says that its skills do not. `/praxis-debug` opens by
telling the human what the symptom argument is for and which of the two
templates its answer selects, then loads `{{skill:status}}`,
`{{skill:diagnose}}`, and `{{skill:session}}` in that order. None of that
framing exists in any of the three skills it composes — it is the command's own
content, and there is nowhere else to put it.

Generated `.cursor/commands/praxis-status.md` has no such content. It opens by
telling the *agent* to run `lambda status --json`, which is verbatim what
`.cursor/skills/recursive-praxis-status/SKILL.md` already says (§0). A command
worth generating is addressed to the person who typed it; that is the line the
current generator does not cross.

## 5. What has to change

### 5.1 The definition type splits

`WorkflowDefinition` currently carries `id`, `title`, `summary`, `body` and is
consumed by both surfaces. It becomes two types — a `SkillDefinition` keeping
today's shape, and a `CommandDefinition` adding the skills it composes:

```ts
export interface CommandDefinition {
  readonly id: string;
  readonly title: string;
  readonly summary: string;
  /** Skill ids this command loads, in the order it loads them. */
  readonly composes: readonly string[];
  readonly body: string;
}
```

`composes` is not decoration — it is what lets generation **fail closed**. A
command naming a skill that does not exist should throw at render time, exactly
as `{{invoke:}}` already throws on an unknown workflow id. A command shipped
pointing at a missing skill is a dead command, and that is a build error, not a
runtime surprise.

### 5.2 The layout interface takes two collections

`HostLayout.filesFor(workflow)` returns a skill and optionally a command from
one definition. It becomes two methods — `skillFilesFor(skill)` and
`commandFilesFor(command)` — so a host can receive seven of one and four of the
other. `StandaloneLayout`'s `commandPath(workflowId)` becomes
`commandPath(commandId)`, and `CommandsOnlyLayout` stops deriving command files
from workflows entirely.

### 5.3 Degradation becomes mandatory, not optional

This is the part §2.3(c) predicts and it is the real risk in the change.

| Host | Gets skills | Gets commands | Under the split |
| --- | --- | --- | --- |
| Cursor | yes | yes | 7 + 4 — fine |
| Claude Code | yes | yes | 7 + 4 — fine |
| Codex | yes | **no** | 7 skills. A skill referencing `{{invoke:debug}}` would name a command Codex never received. |
| opencode | **no** | yes | 4 commands. Every `{{skill:status}}` in them names a skill opencode never received. |

Today this cannot happen: the 1:1 pairing means every reference has a target on
every host. **The split breaks that invariant**, and the two rows above are
live defects the moment a command references a skill.

OpenSpec's answer is the right one and should be ported: resolve every
reference against *what that host was actually given*. Where the target does
not exist, degrade — to the skill spelling, or to prose ("the
`recursive-praxis-status` skill"), or for opencode, inline the needed step
rather than pointing at a file that is not there. `remarkPraxisInvocation`
already has the resolver hook to hang this on; what it lacks is knowledge of
which surfaces the current host received.

### 5.4 The inventory changes shape

Cursor goes from 14 files / 40,279 bytes to 7 skills + 4 commands = 11 files.
The commands are routing documents rather than full procedures, so the byte
total should fall by roughly a third even before counting the removed
duplication. Every count in
[generated-file-inventory.md](generated-file-inventory.md) §0.1 is invalidated
by this change and must be re-measured, not adjusted by arithmetic.

The `{{args}}` transform in §3.1 is a **precondition**, not a follow-up: a
command that cannot receive its argument is the surface this proposal is trying
to stop shipping.

## 6. Summary of the OpenSpec review

| Mechanism | Verdict |
| --- | --- |
| One body → two surfaces, rendered | **RecursivePraxis already does this.** OpenSpec is migrating toward it (`apply-change.ts`) and has not finished (`propose.ts`, 97% hand-duplicated). Do not adopt its content model. |
| Per-host invocation rewrite | Both have it. RecursivePraxis's is better — mdast, not regex. Keep. |
| `delivery: both / skills / commands` | **Adopt.** Makes surface selection explicit instead of implied by layout class. |
| `COMMAND_TO_SKILL_NAME` | **Adopt and extend** to many-to-one via `composes`. |
| Reference degradation to skills / prose | **Adopt — required**, see §5.3. |
| Two template types with distinct metadata | Adopt the *split*; ignore the fact that OpenSpec fills both with the same prose. |

## 7. Today's output, scored against the acceptance test

Using the three criteria from the Frame. Each verdict is against the seven
skills as generated, not against the CLI's capability.

### 7.1 Criterion by criterion

| Criterion | Covered by | Verdict |
| --- | --- | --- |
| 1. Know how to **ask for** a sequence | `intent` (classify → template), `solve` (explicit endpoints) | **Partial.** Both describe *how* to ask once you have decided to. Nothing says *when* a task has reached stage 3. An agent that never enters the layer passes every individual skill and fails the methodology. |
| 2. **Call the verbs** to get the sequence | `diagnose`, `solve`, `analyze` | **Met.** Arguments, JSON shapes, and the `PARTIAL` case are all documented. |
| 3. **Execute** the sequence | `session` (`step`/`bind`/`halira`), `ir`, `check` via `intent` | **Partial** — see 7.2. |

### 7.2 The gap in criterion 1: nothing marks the entry

Each of the seven skills documents one verb. None of them says: *at the start
of a task, before you execute, get a sequence.* The seven describe stage 3's
instruments and never name stage 3.

This is the strongest argument for the command surface in this proposal, and it
is a better argument than the human-convenience one this document opened with.
**A command is a named entry into stage 3.** `/praxis-debug` does not exist
because typing it is faster than typing three `lambda` calls; it exists because
"my work is stuck" is a recognisable moment at which the intent-operation layer
should be entered, and nothing in the current output names such a moment.

### 7.3 A live defect in criterion 3

The `intent` skill, Step 5, as shipped:

> `lambda operators show <Op>`
>
> Do this for each operator, in sequence order, and use the returned meanings
> as the skeleton of your output: one section per operator, ordered as the CLI
> ordered them.

`lambda operators show` returns no meanings. Verified by running it:

```
$ lambda operators show Telo
name: Telo
symbol: →
class: A-Constructive
λ=0.25 (authored)
```

Four lines, none of them a meaning. The instruction is unexecutable as written,
and it sits in the one workflow that carries the whole of criterion 1.

The data exists — `operatorMeaning(op)` backs the `intent` field of each
`legalNext` entry in `statusPayload`
([status-payload.ts](../../src/cli-support/status-payload.ts)) — so this is a
plumbing gap, not a missing capability. Two possible fixes, both code changes
outside this proposal: add the meaning to `operators show`, or point the skill
at `legalNext[].intent`. The first is better; `legalNext` only covers operators
that are legal *now*, not the ones in a sequence being rendered.

This is worth fixing before the command surface is built, not after. Every
proposed command ends by rendering a sequence into instructions, and all of
them would inherit the same dead step.

## Open questions

1. Is `/praxis-commit` the right name given §4's collision with `git commit`?
2. Should the four commands ship at all if a host is skills-only? A Codex user
   gets the whole capability through skills and loses only the typed entry
   point. Or should `delivery: skills` still generate a "command" as a skill,
   the way OpenSpec's skills-only tools invoke `/openspec-propose`?
3. `composes` creates an ordering claim ("load status, then diagnose, then
   session"). Is that ordering enforceable, or is it advisory prose the agent
   may ignore? If advisory, does it belong in a typed field at all?
4. Does the command surface need its own epistemic footer? The current one is
   written to an agent ("do not simulate reserved verbs"). A human reading a
   command file needs a different set of cautions, or none.
5. Four commands is a guess at the right granularity. `/praxis-explore` and
   `/praxis-polish` may be one command with an argument; `/praxis-debug` may
   split by template. Worth deciding from real use rather than up front.
